    14.1. Instalación del SGBD PostgreSQL

    El curso de PHP 7 descargaba el instalador de PostgreSQL para Windows desde el sitio web https://www.postgresql.org/download/, lo ejecutaba y luego cambiaba el servicio de Windows de PostgreSQL, que se iniciaba automáticamente al arrancar el sistema, a un servicio de inicio manual. Con [Laragon], es más simple. PostgreSQL no viene instalado de forma predeterminada, pero [Laragon] puede agregarlo por sí mismo:

    • haga clic con el botón derecho en la ventana de [Laragon] (o en su ícono en la barra de tareas) para abrir su menú;
    • seleccione [Tools > Quick add]. La lista muestra el software que [Laragon] puede descargar e instalar, entre ellos una o varias versiones de PostgreSQL, como [postgresql-17];
    • al hacer clic en la versión deseada se inicia la descarga y la instalación. PostgreSQL se instala en la carpeta [<laragon>/bin/postgresql], y sus datos en la carpeta [<laragon>/data/postgresql-NN];
    • El botón [Start All] ahora inicia PostgreSQL junto con Apache y MySQL. La ventana de [Laragon] indica que está escuchando en el puerto 5432, su puerto predeterminado.

    Si la versión de PostgreSQL deseada no aparece en la lista, puede agregarla: el menú [Tools > Quick add > Configuration] abre el archivo [<laragon>/usr/packages.conf], que asocia cada programa con la dirección de su archivo comprimido. Agregue (o modifique) una línea con el formato [postgresql-17=<address of the zip archive>], donde el archivo comprimido es el archivo de “binarios” de PostgreSQL para Windows que proporciona la empresa EDB (el enlace “zip archive” de la página https://www.enterprisedb.com/download-postgresql-binaries). Como alternativa, sin usar este menú, puede extraer usted mismo este archivo comprimido en una subcarpeta de [<laragon>/bin/postgresql]: [Laragon] la encontrará la próxima vez que se inicie, y la versión que se va a usar puede seleccionarse en el menú [PostgreSQL > Version].

    PostgreSQL se utiliza solo en este capítulo y en el siguiente. Funciona únicamente cuando [Laragon] está en ejecución, y puede detenerlo desde el menú [PostgreSQL] de [Laragon].

    Al igual que MySQL, PostgreSQL tiene un administrador, el superusuario [postgres]. En la instalación realizada por [Laragon], normalmente no tiene contraseña. Si se le asignó una contraseña, las herramientas la solicitarán.

    La terminal de [Laragon] da acceso al cliente de línea de comandos de PostgreSQL, [psql], que equivale al cliente [mysql]. El menú [PostgreSQL] de [Laragon] también ofrece la herramienta gráfica [pgAdmin] cuando está instalada. La documentación de PostgreSQL está disponible en https://www.postgresql.org/docs/.

    Comentarios

    • Líneas 7–8: eliminamos la base de datos y el usuario si existen, para que el script pueda volver a ejecutarse. Con PostgreSQL, un nombre que contiene un guion se encierra entre comillas dobles, y no entre acentos graves como en MySQL: esta es la primera diferencia entre los scripts de los dos SGBD;
    • Línea 9: PostgreSQL llama “roles” a sus usuarios. El atributo [LOGIN] autoriza al rol [admtaxes] a conectarse al SGBD;
    • Línea 10: creación de la base de datos [dbtaxes-2019]. Su propietario es [admtaxes], lo que le otorga todos los derechos sobre la base de datos. La codificación de caracteres es UTF-8. La base de datos se construye a partir de la base de datos plantilla [template0], que admite cualquier codificación de caracteres;
    • Línea 13: esta línea no es un comando SQL sino un comando del cliente [psql] (empieza con una barra invertida). Conecta el cliente a la base de datos [dbtaxes-2019] que acaba de crearse. Con PostgreSQL no existe un equivalente del comando [USE] de MySQL: una conexión opera sobre una sola base de datos;
    • Línea 16: los comandos siguientes se ejecutan con la identidad de [admtaxes], que será, por lo tanto, el propietario de las tablas creadas;
    • Líneas 19–25: la tabla [tbbrackets]. La clave primaria [id] es de tipo [INTEGER GENERATED ALWAYS AS IDENTITY]: es el SGBD quien genera sus valores durante las inserciones, igual que lo hacía el atributo [AUTO_INCREMENT] en MySQL. Esta sintaxis se ajusta al estándar SQL; [AUTO_INCREMENT] es específico de MySQL. El tipo [NUMERIC] equivale al tipo [DECIMAL] de MySQL;
    • Líneas 28–41: la tabla [tbconstants]. Los nombres de las columnas se escriben en minúsculas, con las palabras separadas por guiones bajos (half_share_qf_ceiling).

    ¿Por qué estos nombres de columnas? Una particularidad de PostgreSQL es que los nombres de las columnas pueden distinguir mayúsculas de minúsculas, lo que normalmente no ocurre con otros SGBD. Por ejemplo, con MySQL, la consulta [select limits, coeffR, coeffN from tbbrackets] funciona aunque las columnas reales de la tabla [tbbrackets] sean [LIMITS, COEFFR, COEFFN]. Con PostgreSQL, no funciona, porque PostgreSQL convierte a minúsculas los nombres que no están entre comillas: en realidad ejecuta el comando [select limits, coeffr, coeffn from tbbrackets]. Para evitarlo, hay que usar [select "LIMITS", "COEFFR", "COEFFN" from tbbrackets], es decir, encerrar los nombres de las columnas entre comillas. Por estas razones, damos a las columnas nombres en minúsculas, y no podemos reutilizar los nombres en camelCase (halfShareQfCeiling) de la base de datos MySQL. Los nombres de los objetos de una base de datos pueden ser una fuente de incompatibilidad entre SGBD, ya que algunos nombres son palabras reservadas en ciertos SGBD pero no en otros.

    • Línea 102: el archivo [database-nonexistent-user.json] describe la base de datos con un usuario llamado [unknown], que PostgreSQL no reconoce. La conexión falla, y la capa [dao] lanza una excepción [TaxException] con el código 30.

    ¿Por qué este cambio? Para cada tipo de conexión, un servidor PostgreSQL elige un método de autenticación especificado en su archivo de configuración [pg_hba.conf] (en la carpeta de datos de PostgreSQL, [<laragon>/data/postgresql-NN] con [Laragon]). El método [scram-sha-256] verifica la contraseña. El método [trust], en cambio, confía en el cliente: acepta la conexión sin verificar la contraseña, siempre que el usuario exista. Este es el método que utiliza la instalación de PostgreSQL creada por [Laragon] para las conexiones que provienen de la máquina local, lo que explica por qué el superusuario [postgres] no tiene contraseña. Con esta configuración, se acepta una contraseña incorrecta: la prueba de “contraseña incorrecta” fallaría, ya que no se lanza la excepción esperada. Un usuario inexistente, en cambio, es rechazado sea cual sea el método de autenticación: la prueba funciona en todas las instalaciones. El método [trust] es cómodo en una máquina de desarrollo; obviamente, no debe usarse en un servidor de producción.
